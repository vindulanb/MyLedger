## Ground rules that apply to every step in this file

1. Write the UI in [Dioxus](https://dioxuslabs.com/), targeting Android (`dx build --platform android`), inside `apps/mobile`.
2. This app reads the phone's own SMS inbox to auto-detect transactions — that capability is **mobile-only**; it never exists in the web app.
3. Money is `i64` cents everywhere; format to currency only at render time.
4. Never log or display raw SMS bodies, account numbers, or auth tokens — redact them in any debug output.
5. The app must stay fully usable for manual entry if SMS permission is denied — never block the rest of the app on it.
6. Every step is idempotent — extend what already exists rather than duplicating it.
7. No sample/demo financial data, ever, at any step.

Get a minimal "Hello MyLedger" screen building and running on an Android emulator via the Dioxus CLI (`dx build --platform android` / `dx serve`), including whatever Android SDK/NDK/`cargo-ndk` toolchain setup is required — document any one-time environment setup steps you had to do in a short `apps/mobile/SETUP.md`.

On successful pairing and on each app launch, pull `GET /api/v1/state` and populate this local cache so the app has something to show even before you've built any real screens.

## Step 4: SMS parsing engine (pure logic)

**Prompt:**

Create a new crate `crates/sms_parser` in the MyLedger workspace (kept separate from `apps/mobile` so it's pure, platform-independent, fully unit-testable logic with no Android dependencies). Define:

- A `SmsParseRule` struct mirroring the backend's `sms_parse_rules` table: label, sender_pattern, body_regex (with named capture groups), amount_group, merchant_group (optional), date_group (optional), kind_hint (`Debit`/`Credit`/`Auto`), account_hint (optional), default_category_id (optional), enabled.
- A function `match_sms(rules: &[SmsParseRule], sender: &str, body: &str, received_at: DateTime) -> SmsMatchResult` where `SmsMatchResult` is one of: `NoMatch` (no enabled rule's sender_pattern matched — this SMS isn't a bank alert, ignore it silently), `Matched(ParsedTransactionCandidate)` (exactly one rule produced a valid extraction), or `Ambiguous(Vec<ParsedTransactionCandidate>)` (more than one rule matched with different results — this must be routed to a review queue, never guessed).
- `ParsedTransactionCandidate` should carry everything needed to build a `core::Transaction`: amount_cents, merchant (fallback to the SMS sender if no merchant group captured), date (fallback to `received_at`'s local date if no date group captured, normalized to `YYYY-MM-DD`), kind (resolved from `kind_hint`, or from a keyword in the captured `kind` group when `kind_hint` is `Auto` — e.g. "debited"/"spent" → expense, "credited"/"received" → income), account (from `account_hint` if present), default_category_id.

Write thorough unit tests: a clean single-rule match with all groups; a match using only the required `amount` group with sensible fallbacks for the rest; two enabled rules whose patterns both match the same sender/body producing `Ambiguous`; an SMS from an unrecognized sender producing `NoMatch`; a rule with `kind_hint = Auto` correctly inferring debit vs. credit from keywords in the message body. Run `cargo test -p sms_parser` and confirm everything passes.

**Quick check:**

- `cargo test -p sms_parser` passes.
- Read 2–3 of the ambiguous-match and no-match test cases yourself to confirm the engine genuinely never guesses.

## Step 5: SMS permission, JNI bridge & initial import

**Prompt:**

In `apps/mobile`, wire up real SMS inbox reading on Android:

1. Declare `android.permission.READ_SMS` and `android.permission.RECEIVE_SMS` in the Android manifest. Build a clear explanation screen (why the app wants this, that it's fully optional, and that manual entry works fine without it) that's shown *before* the system permission dialog — never request it silently on launch.
2. Implement a small `android_sms_bridge` module using the `jni`, `ndk-context`, and `ndk` crates: get the JNI environment via `ndk_context::android_context()`, call into `Context.getContentResolver().query(Uri.parse("content://sms/inbox"), ...)`, and read back `address` (sender), `body`, and `date` for each message. Keep any actual Kotlin/Java code to the absolute minimum necessary — only add a Kotlin file if a required Android API genuinely can't be reached via raw JNI from Rust, and if you do, document exactly why in a code comment.
3. Build the **initial import flow**: the first time permission is granted, show a one-time choice — "Import past messages from: Last 7 days / Last 30 days / Last 90 days / All time" — then read that range from the content provider, run every message through `sms_parser::match_sms` (Step 4) using whatever rules currently exist in the local cache (there won't be any yet unless you add a couple manually during testing — that's expected and fine, the Parsing Rules manager UI comes in Step 7).
4. Show a review screen listing the results, split into "Will be added automatically" (a clean single-rule match) and "Needs your review" (ambiguous or no usable amount) — let the user bulk-approve the clean matches or edit/skip individually. Nothing is written to the local transactions table until the user confirms.
5. If permission is denied, confirm the rest of the app remains fully functional.

**Quick check:**

- Create at least one test SMS parsing rule (you can insert it directly into the local cache/backend for this test, since the management UI doesn't exist until Step 7), send yourself a matching test SMS, grant permission, run the initial import, and confirm it's correctly categorized into the "will add automatically" bucket with the right extracted fields.
- Send a non-bank SMS (e.g. a normal text) and confirm it's silently ignored, not treated as a candidate.
- Deny the permission on a fresh install and confirm the rest of the app still works.

## Step 6: Ongoing SMS capture, offline queue & sync

**Prompt:**

In `apps/mobile`, build ongoing (not just one-time) SMS capture and get it syncing reliably to the backend:

1. Register a native `BroadcastReceiver` for `android.provider.Telephony.SMS_RECEIVED` so new messages are parsed the moment they arrive. If this proves unreliable to wire up cleanly within Dioxus's Android activity lifecycle after a genuine attempt, fall back to: polling `content://sms/inbox` for anything newer than a persisted `last_seen_sms_timestamp` every time the app is foregrounded, plus a periodic WorkManager job (every 15–30 minutes) for background capture. Tell me in your response which approach you ended up using and why.
2. Before parsing any message, check its `sha256(sender + body + timestamp)` against the local `processed_sms` table (from Step 1) — never parse the same message twice, even across app restarts.
3. Every SMS that resolves to a clean single-rule match (via `sms_parser::match_sms`) is written straight to the local transactions cache with `source = 'sms'` and `pending_sync = 1`. Ambiguous or unmatched-but-plausible messages go to a pending review queue (a new local table is fine) rather than being silently dropped or silently inserted.
4. Build a background sync task: whenever connectivity is available, push every `pending_sync = 1` local transaction to `POST /api/v1/sms-transactions` on the backend in a batch (add this endpoint to `crates/server` now if it doesn't already exist — same validation/fingerprint-dedupe path as `/api/v1/transactions`, just tagging `source = 'sms'`), clear `pending_sync` on success, and leave it set to retry on failure. Then pull a fresh `GET /api/v1/state` to reconcile the local cache (so edits made from elsewhere, e.g. the web app, show up on the phone too).
5. Add a small, persistent sync-status indicator somewhere in the UI (e.g. "Synced just now" / "3 pending — will sync when online") — don't make sync state invisible.

**Quick check:**

- Turn on airplane mode, receive/trigger a test SMS that matches a rule, confirm it appears locally as pending with the sync indicator reflecting it.
- Turn connectivity back on, confirm it syncs and shows up via `GET /api/v1/state` from the backend.
- Send the exact same test SMS content twice and confirm it's only ever parsed/inserted once.
